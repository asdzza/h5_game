# H. 体验评审与优化建议（外部玩家 / 评委视角）

| 项目 | 内容 |
|---|---|
| 评审对象 | 《撞个正着》 v0.1.0，50 关完整版（`main` @ `c219936`） |
| 评审日期 | 2026-11-10 |
| 评审视角 | 第一次接触本作的玩家 + 作品评委。**刻意不使用开发期的任何假设**，只按"打开即玩"的真实路径体验 |

## 0. 评审是怎么做的（可复现）

1. **真实设备尺寸试玩**：在 390×844、375×667、360×640、320×568、1000×700（桌面）、844×390（横屏）六种视口下运行 `npm run dev`，用浏览器设备模拟逐关试玩第 1–8、19–25、43–50 关。
2. **全量数据校核**：`npm run verify` 通过（`levels=50 failed=0`）；另用 `research/s4_core.mjs` 的 `analyze()` 对 50 关做全量求解，得到每关的 par、步数上限、首手解数、最优首手数、最差首手、超限首手数、"压力步"数量、停靠来源分布。
3. **合成输入测试**：向 canvas 派发 `pointerdown/pointermove/pointerup`，测量提交阈值、撤回手势、动画期间点击等边界行为。
4. **布局实测**：用 `getBoundingClientRect` / `scrollWidth` vs `clientWidth` 检查 HUD、选关页、结算页是否溢出或被裁切。
5. **可访问性**：按 WCAG 2.1 计算对比度；对五种方块色做 protan / deutan 模拟后计算 CIE76 ΔE。
6. **文档对照**：逐条比对 `docs/D_游戏设计文档.md`（§4 反馈时序、§5 撤销/失败/提示、§9 UI、§4.3 星级奖励）与实际实现。

> 说明：本文只做评审与建议，**未修改任何游戏代码**。文中的行号对应评审时的 `main` 分支。

## 1. 结论

### 1.1 一句话

> 这是一个"规则一句话说得清、想赢却要想三步"的好点子，但玩家在屏幕上**感受不到自己做了什么**——没有撞击的回弹、没有消除的顿帧、拖拽时看不到落点；62% 的关卡里最低一档星星在数学上不可能拿到，而"提示"按钮永远在最显眼的位置，随时可以把整关的思考一键抹平。

### 1.2 评分卡（10 分制，休闲解谜品类内部比较）

| 维度 | 分数 | 一句话理由 |
|---|---:|---|
| 核心规则创意 | **8.5** | "消除 = 拆掉自己的刹车"是真创新，且一句话能讲清 |
| 关卡数据的严谨度 | **8.0** | 50 关全部求解器验证，par 与 limit 有据可依，这点超过大多数同类作品 |
| 操作手感 / 反馈 | **4.5** | GDD 里设计的顿帧、粒子、挤压、震屏、虚影、方向箭头**一个都没实现** |
| 关卡编排与新鲜感 | **5.5** | 50 关只有 2 种目标 + 1 种新元素（墙），中段开始明显重复 |
| 难度曲线与反馈闭环 | **5.5** | 1★ 在 31/50 关里不可达；撤销退步数使"上限"形同虚设 |
| 视觉风格 | **7.0** | 石材 + 渐变 + 昼夜双主题统一、耐看；但外框吃掉近一半棋盘面积 |
| 信息架构 / UI | **5.0** | 320–360px 下 HUD 文字被裁；选关页不给关卡名、不自动定位当前关 |
| 可访问性 | **3.0** | 颜色是唯一线索；deuteranopia 下紫与蓝 ΔE≈1.8，11 关无法推理 |
| 工程与可维护性 | **7.0** | 模块划分干净、求解器与运行时同构；但 `npm test` 本机跑不完、生产包暴露调试接口 |
| **综合** | **6.0** | "值得做完"的作品，不是"已经做完"的作品 |

## 2. 第一印象：前 10 分钟我实际经历了什么

按真实玩家路径记录（390×844 手机视口）：

| 时刻 | 我看到 / 感觉到 | 判断 |
|---|---|---|
| 打开页面 | 直接进入第 1 关。没有标题、没有 logo、没有"点一下开始"。顶部一排按钮，中间一块深色石框棋盘 | 像个 demo 页面，不像一款"上架的游戏"。第一眼没有任何作品名和调性 |
| 第 1 关 | 两个红块相隔一格，教我怎么拖。拖动时方块跟着手指走 | 明白了规则，但**拖动过程中没有任何"会滑到哪"的提示**，松手才知道 |
| 第一次消除 | 两块消失，配一声"叮"。没有顿帧、没有粒子、没有震屏 | 手感偏"空"。这是本作最高光的瞬间，却和"关掉一个开关"的反馈强度差不多 |
| 第 2–5 关 | 学会了"停住"和"用墙刹车" | 规则吸收了，觉得聪明 |
| 第 6–12 关 | par 从 4 跳到 6，出现内墙 | 开始有意思；但**没有任何"新机制登场"的提示**，玩家不会意识到"墙变多了" |
| 第 13–18 关 | 依旧清空全场，par 6–8、上限 9–11，棋盘更大、墙更多 | 开始有"又是一关"的疲劳感：目标没变，只是块更多了 |
| 第 19 关 | 突然出现"只清红块"，par 从 8 掉到 3 | **这是全作第二重要的机制，却被放在第 19 关**，且没有一句话说明它为什么、和之前的关卡什么关系 |
| 第 20–30 关 | 目标色几乎永远是红色 | 目标其实是"不要消红色以外的块"——换个颜色完全等价，18 关目标关里 15 关都是红 |
| 第 31 关以后 | par 8–10，最长一关 10 步，但界面上"步数 0/12"的大小和 3 步关一模一样 | 难度靠"算"而不是"看"，屏幕上感受不到它在变难 |
| 失败时 | 弹出一个铺满屏幕的模糊遮罩，"步数用完了" | 和 GDD 设计的"上方半透明条"完全不同，仪式感更重、压迫感也更强 |
| 点"撤销" | 只想撤回刚刚那一步，结果**有时没反应**（见 4.1） | 直接的挫败，且玩家无法理解原因 |
| 打开选关 | 50 个数字格子，10 行，当前关在屏幕外，只看到第 1–30 关 | "我打到哪了？"需要自己找 |

**第一印象的总结**：规则get到了，但**没有"这款游戏很用心"的感觉**。原因不是画面不好看，而是缺少三个东西：开场（作品的存在感）、反馈（操作的结果感）、路标（我在哪、接下来会有什么）。

## 3. 值得保留的（先说明，避免后面全是批评）

1. **"消除 = 拆除刹车"这个点子是真的好。** 多数滑动解谜的消除都是纯收益，本作让它同时是损失，玩家必须在"清掉一对"和"留着它当墙"之间做取舍。这不是换皮，是机制层面的微创新，值得围绕它做完整款游戏。
2. **关卡数据是全作最硬的部分。** 50 关全部有 solver 验证的 par，`limit` 不是拍脑袋，`research/` 里有一套可复用的生成 + 验证流水线。这在个人作品里是稀缺资产——**问题只在于这些数据没有转化成玩家能感知到的东西**。
3. **视觉语言统一。** 石材外框 + 左上柔光 + 圆角方块，昼夜两套主题，配色克制（不是常见的糖果色），有辨识度。
4. **零资源依赖。** 音效用 WebAudio 合成，无外部素材，加载快、可离线、包体小，工程上很干净。
5. **移动端不炸版。** 棋盘自适应、无横向滚动、iOS/Android 都能玩，这在 H5 作品里已经是合格线以上。
6. **规则层与渲染层分离干净。** `game.js` 纯函数、`render.js` 只画、`input.js` 只管手势，改起来不怕连锁崩，后续加机制成本低。

## 4. 手感：作为"动作"的那一下（最需要补的部分）

> 这一节是全篇最重要的。GDD §4.1 用一整张表规定了"一次操作的反馈时序"，实现度约为 **15%**：只有滑动补间和两声合成音，其余全部缺失。

### 4.1 【P0】动画期间点"撤销"会被静默吞掉

- **现象**：移动后立即点"撤销"，按钮是亮的、有 hover 反馈，但点了没有任何反应。
- **证据**：`src/main.js:503` `undo()` 第一行 `if (won || anim || !history.length) return;`；而 `updateUndo()`（`src/main.js:137`）只根据 `history.length` 决定 disabled。滑动动画约 400 ms，这 400 ms 内按钮"看起来可用、实际无效"。
- **影响**：撤销是本作唯一的容错手段，也是"手滑"的唯一出口。一次无效点击会让玩家直接怀疑游戏坏了，而不是怀疑自己点早了。
- **建议**（二选一，推荐 A）：
  - A. 动画期间点击 → **记入队列**，动画结束后立刻执行撤销（体验最好，改动集中在 `undo()`）。
  - B. 至少把按钮在动画期间置灰，让"不可用"可见。

### 4.2 【P1】消除没有"砰"

- **现象**：同色相撞 → 两块直接消失 + 一声叮。
- **GDD 设计**：40 ms 全屏顿帧 → 放大 1.15 → 180 ms 缩到 0 + 6 个碎片粒子 → 80 ms 轻震 4 px / `vibrate(15)`。
- **影响**：消除是唯一的正反馈事件，也是本作的核心动作。当前它和"关掉一个开关"的反馈强度几乎一样，**玩家不会为了再看一次消除而想多消一对**。
- **建议**：按 GDD 实现，最小可行版本 = 60 ms 命中停顿（`anim` 里加一个 `hitstop` 阶段）+ 8 个粒子（canvas 画圆即可，无需图片）+ 逐步衰减的 `ctx.translate` 抖动。半天工作量，回报最高。

### 4.3 【P1】撞墙 / 撞异色没有"刹住"

- **现象**：方块滑到墙或异色块前，硬停在格子上。
- **GDD 设计**：停靠瞬间 60 ms 挤压（`scaleX 1.12 / scaleY 0.9`）后回弹。
- **影响**：本作有一半的操作是"停住"而不是"消除"。停住的反馈缺失，等于一半的动作没有回应；而且玩家不容易分清"我是撞墙停的"还是"我撞到别的块停的"——这两件事在策略上完全不同。
- **建议**：停靠时按撞到的对象做**不同**的挤压与音高（墙：闷、低；异色块：更脆、略高），并给被撞的块一个 1 px 的描边闪。

### 4.4 【P1】拖拽时看不到"会滑到哪里"

- **现象**：手指拖动方块，只有被拖的方块位移，没有落点虚影、没有方向箭头、没有被撞目标的描边。
- **GDD 设计**：拖动 > 10 px 出现方向箭头 + 落点虚影 + 被撞目标描边。
- **影响**：这是策略游戏里最关键的一条"预判信息"。没有它，玩家只能靠**心算 + 试错**；而本作的错误代价是"拆掉自己的刹车"，往往要到 3 步之后才发现。**玩家会把"我没想到"记成"游戏不讲理"**。
- **建议**：这是投入产出比最高的一项。`legalMoves()` 已经返回了完整落点信息，画一个半透明轮廓 + 一条虚线箭头即可，规则层零改动。

### 4.5 【P1】10 px 阈值太敏感，且没有"取消"手势

- **现象**：`THRESHOLD = 10`（`src/input.js:3`）。实测 11 px 的轻微竖向抖动即提交一步；8 px 的对角位移（模长 11.3）也提交。拖出去再拖回原点，松手仍然提交。
- **影响**：手机单手持机时，拇指按下的瞬间常有 6–12 px 的位移。玩家会遭遇"我明明只想点一下看看"的误操作，而本作的误操作代价是**不可逆地拆掉一对刹车**。
- **建议**：
  - 阈值提到 18–24 px（或按 `devicePixelRatio` 换算）；
  - 实现"拖回起点 12 px 内松手 = 取消"（这是触屏滑动解谜的通行约定）；
  - 拖动未超过阈值时不锁定方向，超过后允许在 45° 边界上"换向"，而不是一旦锁定就不再变化（`input.js:36` 当前会重算，这点是对的，保留）。

### 4.6 【P2】结算没有"省了几步"的仪式

- **现象**：通关直接弹结算卡，步数直接出现在文字里。
- **GDD 设计**：结算前 200 ms 剩余步数逐个跳动。
- **建议**：`0 → 剩余步数` 的数字滚动 200 ms，配一声随步数上升音高的 tick。成本极低，但直接决定"要不要再刷一次三星"。

### 4.7 【P2】撤销不是"倒放"

- **现象**：撤销瞬间跳回上一个局面。
- **GDD 设计**：反向动画 120 ms。
- **建议**：120 ms 的反向补间 + 反向音效。玩家需要**看见**"我刚才那一步被还回来了"，否则会怀疑是重开。

## 5. 推进与新鲜感

### 5.1 【P1】50 关里只有 2 种目标、1 种新元素

- **证据**：`src/levels.js` 中 `goal` 只有 `clear`（32 关）和 `color`（18 关）；棋盘元素只有"方块"和"墙"（48/50 关有内墙，0 关有其他元素）。
- **问题**：第 1 关教的东西，第 50 关还在用。变化只来自"块的位置 + 墙的位置 + 颜色数量"，玩家在中段（约 20 关后）就会形成"我知道这关要干什么了"的预期。
- **对比同类**：一个 50 关的滑动解谜，通常会每 8–12 关引入一个**新动词**（例：可推动的障碍、单向门、锁定块、计时块、必须按顺序消除的链）。
- **建议**（按性价比排序，规则层改动都很小）：
  1. **目标色轮换**：立即可做，18 关目标色改成红/蓝/绿/黄/紫均衡分布（见 5.3）。
  2. **"必须最后消"的目标**（指定一对必须在最后消除）：复用现有规则，只改胜负判定。
  3. **固定块（不可拖动）**：天然是"永久刹车"，会把关卡的解法空间压缩得很漂亮，只需在 `rows` 里加一个字符。
  4. **单步限制变体**（如"只能消 3 对"）：改 `limit` 语义，用来做"节奏关"。
- **重要**：**不用担心加机制会破坏已有 50 关**——新元素只用于新增的第 51 关以后，或作为 S6 的专属机制。现有 50 关的价值是"已证实的 par 数据"，不需要重做。

### 5.2 【P1】`stage` 字段存在，但玩家永远看不到

- **证据**：`levels.js` 的 `stage` 分布为 S1=8、S2=10、S3=12、S4=10、S5=10；全项目**没有任何一处读取 `stage`**（选关页是 5×10 的一整块数字，无分组、无名、无章节标题）。
- **影响**：开发者心里的"五个阶段、五次难度跃迁"，在玩家眼里是"50 个连着的数字"。这是最可惜的一处——数据已经分好组了，UI 却没有把它讲出来。
- **建议**：
  - 选关页按 stage 分 5 段，每段一个标题 + 一句话主题（"学会停住" / "用墙刹车" / "只清目标色" / "双刹车" / "终局"）；
  - 每段最后一关做成"小结关"（GDD §6.9 已有此设计），通关时给一个阶段完成页（`§4.3` 已设计，未实现）；
  - 至少在第 1、6、19、31、41 关开始前加一张 1 屏的机制卡（"这关开始，你要学会……"）。

### 5.3 【P1】目标色严重偏红

- **证据**：18 个 `color` 关里 `targetColor: 1`（红）**15 关**，蓝 1 关（#26），绿 2 关（#23、#29）；黄、紫作为目标 **0 关**。
- **影响**：目标色的颜色本身不影响难度（规则对称），但它决定了**视觉记忆点**。15 关都是"清红块"，玩家记不住任何一关；而"只清紫色"会立刻成为记忆锚点。同时这浪费了调色板里两个已经实现的颜色。
- **建议**：把目标色当作**主题而非难度**来分配——每个颜色 3–4 关，且让同色关卡在棋盘形态上也有差异。纯数据改动，半小时可完成，需要重新跑一次 `verify`。

### 5.4 【P1】`teach` 在中后期直接泄题

- **证据**（原文摘录）：
  - #43 `第一手先消最上面一对…`
  - #44 `蓝块先上提…`
  - #48 `蓝块先落到底边占位`
  - #50 `红块第二步就要停在紫块旁边…`
- **问题**：GDD 的意图是"`teach` 只讲新机制"。当前它变成了**免费的分步攻略**，而且是自动弹在提示条上的（`setHint(level.teach)`，见 `showHint` 旁的调用与 `undo()` 里的 `setHint(level.teach)`）。
- **影响**：`teach` 在每次撤销后都会重新显示。也就是说，一个玩家只要按一次撤销，就会拿到当局的最优开局——**星级评估失去意义**。
- **建议**：`teach` 拆成两类：
  - `tip`：机制说明（"撞到异色块会停住"），常驻可查；
  - `nudge`：解法提示，只在"看解法"里出现，且计入星级（见 6.4）。
  并把现有 50 条 `teach` 全面清洗一遍，凡是出现"先/再/第一步/第二步"的句子一律移出。

### 5.5 【P2】重名关卡

- **证据**：#4 与 #22 都叫「只要红色」。
- **建议**：改一个名字。玩家在选关页上是靠名字回忆关卡的，重名等于少了一个记忆点。

### 5.6 【P2】par 曲线在阶段边界锯齿

- **证据**：S2 末尾 par 8 → S3 开头 par 3（#18 → #19）；S3 末尾 par 7 → #34 突然 par 10。
- **说明**：这在设计上是**对的**（新机制引入时难度回撤是标准做法），但**玩家看不到这条曲线**，所以体验上是"难度突然没了，又突然变难"。
- **建议**：配合 5.2 的章节标题，在每段开头明确写出"这一段会更容易，因为你要学新东西"。

## 6. 难度、步数上限与星级

### 6.1 【P1】1 星在 31/50 关里**不可能拿到**

- **证据**：星级规则是 `3★ = moves ≤ par`、`2★ = moves ≤ par+2`、`1★ = 其余通关`；而 `limit` 在 **28 关**等于 `par+2`、**3 关**等于 `par+1`（#4、#43、#48）。也就是说，这 31 关里"能赢"的最差成绩恰好是 2 星，1 星这一档**在数学上不可达**。1 星只存在于前 25 关中的 19 关（`limit > par+2` 的关卡：1、6–22、25）。
- **影响**：
  - 从第 26 关起，星级系统退化成**两档**，而玩家不知道这件事；
  - 更糟的是"上限"和"2 星"是同一条线：**只要没失败，你最差也是 2 星**。星星不再表达"你走得怎么样"，只表达"你有没有触发 3 星"。
- **建议**（三选一）：
  - **A（推荐）**：把 `limit` 统一放宽到 `par+4`，让 1 星重新有意义；失败线退到"真的没救了"的位置。这会显著改变难度，需要对 50 关重跑一次 `analyze` 确认仍有解（数据流水线现成，成本可控）。
  - **B**：删掉 1 星，改成 `3★ / 2★` 两档 + "一次过"徽章，坦诚地做两档制。
  - **C**：保留现状，但在结算页明确写出"本关最低 2 星"，至少不欺骗玩家。
- **不建议**：什么都不做。当前状态是"显示了三档，实际只有两档"。

### 6.2 【P1】撤销退步数，让"步数上限"形同虚设

- **现状**：`undo()` 会 `moves = prev.moves`（`src/main.js:507`），即退还 1 步；失败弹窗里的「撤销一步」也走这条路。
- **实测**：步数 6/6 → 失败弹窗 → 点「撤销一步」→ 步数变回 5/6，弹窗消失，游戏继续。
- **判断**：**这在休闲向设计里是正确的**（GDD §5 明确论证过：约束的是"这一遍的长度"，不是"总思考量"）。问题不在机制，在**表达**：`limit` 在 UI 上和 `par` 并排显示，玩家会以为它是硬约束，结果发现可以无限"借步"。
- **建议**：不改变机制，改文案——把 `limit` 表述成"本关最多 N 步（可撤销回退）"，或在步数条上明确区分"已用步数"与"本次尝试上限"。**别让玩家自己去发现这个漏洞。**

### 6.3 【P1】"压力步"分布说明后期难度是"算"出来的，不是"感觉"出来的

- **证据**（求解器 + 规则层统计）：`pressure`（最优路径中"走错就会多花一步"的关键分叉数）在 S1–S3 大多为 **0–1**，到 S4–S5 才升到 **2–5**；同时每关开局的合法首手数从早期的 **7–10** 个涨到后期的 **16–23** 个（#45 有 23 个），其中大部分都会让你多花步数。
- **解读**：后期确实变难了，但难度来自"满盘二十来条看起来都对的起手，只有少数能走到 par"，这是一种**纯计算型难度**，屏幕上没有任何提示。配合 4.4（无落点预览），玩家会觉得"我漏看了什么"，而不是"我想不出来"。
- **建议**：既然难度已经是"多选项择优"，就应该把**选项本身可视化**——落点虚影（4.4）会直接把"4 个候选首手"变成"4 条可视路径"，让难度从"记忆力"回到"判断力"。

### 6.4 【P1】提示不计成本，且提示内容常常是错的

- **证据 1（不计成本）**：`showHint()` 没有任何使用记录，不扣星、不降评级；`看解法` 按钮**永远可用**，一点即出完整分步答案（`nudge` 是完整解法）。
- **证据 2（内容错误）**：`src/main.js:145` `const popsNow = legalMoves(state).filter((m) => m.res === 'pop').length;`——**统计了所有颜色的可消对，包括非目标色**。实测 #24 开局有 2 对绿色可消，但目标是红色，提示却说"现在有 2 对能直接消，先比较消掉哪一对会拆掉后面的停车位"，会直接把玩家引向错误方向（消绿色 = 扣分/浪费步）。
- **证据 3（不具体）**：GDD 设计的是"高亮最优解的下一步"；实现是三条**通用文案**，任何关卡、任何局面都只有这三句。
- **影响**：提示是新手唯一的救援绳，现在这根绳子会把人往错的方向拽。
- **建议**：
  1. `popsNow` 只统计 `m.res === 'pop' && 目标色匹配`（一行改动）；
  2. 提示加一条**具体信息**："本关还要清 3 对红块，当前 1 对可直接消"；
  3. 按 GDD 补上"使用提示 → 本关最高 2 星"，并把这个代价在点击前就显示出来（"用提示会把本关上限降到 2 星，继续？"）；
  4. `看解法` 收进提示面板的二级入口，或至少加一道"这关的答案会直接显示"的确认。

### 6.5 【P2】`limit` 与 `par` 的展示没有区分

- **现象**：HUD 只有一个"步数 3 / 8"，玩家不知道 8 是上限还是目标。
- **建议**：`已用 3 · 上限 8 · 三星 5`，或把 par 做成步数条上的一个刻度标记（最直观：步数条走到 par 位置时变色）。

### 6.6 【P2】无死局检测 / 无"已经没救了"的提示

- **现状**：目标色清不完但还有合法步时，游戏不做任何提示（GDD 明确说这是**有意为之**："让玩家自己发现"）。
- **判断**：理念可以保留，但对休闲玩家过于残酷——本作的"没救"往往是**很早以前**的一步造成的，玩家会带着"我还有机会"的错觉走完 5 步。
- **建议**：给一个**延迟出现**的弱提示（例如连续 2 步后仍无解 → 提示条显示"现在的局面可能已经清不完目标色了"），或者只在高难度关卡（S4–S5）开启。比"什么都不说"更友好，比"立刻判负"更不伤自尊。

## 7. 界面与布局

### 7.1 【P0】320–360 px 宽度下 HUD 文字被裁切

- **实测**（`scrollWidth` vs `clientWidth`）：

| 视口宽度 | 关卡名「只要红色·入门」 | 目标「目标：只清红块」 |
|---:|---|---|
| 320 | 125 / **70** ❌ | 88 / **33** ❌ |
| 360 | 125 / **110** ❌ | 88 / **73** ❌ |
| 375 | 125 / 125 ✅ | 88 / 88 ✅ |

- **原因**：`.hud-right` 固定 210 px（步数胶囊 50.5 + 4 个 30 px 图标 + 8 px 间距），在 320 px 屏上把左侧文字挤到只剩 70 px。
- **影响**：320×568 是 iPhone SE 一代 / 大量低端安卓的尺寸，**这是真实存在的用户群**；被裁掉的还偏偏是"这关要我干什么"。
- **建议**：
  - 图标区做响应式：`@media (max-width: 380px)` 下缩到 3 个图标（把"重开"收进溢出菜单），或图标缩到 26 px；
  - 关卡名与目标改为允许换行（`white-space: normal`），或目标行改为第二行独占；
  - 更好的做法：**目标信息不再依赖文字**，用目标色小圆点 + 剩余对数表示（"🔴 ×3"），天然省空间。

### 7.2 【P1】棋盘外框吃掉近一半面积

- **实测**（390×844）：格子 50 px，7×7 整盘 350 px，**可玩区只有中间 5×5 = 250 px**，外框占整盘面积 **49%**。屏幕上下还各有约 121 px 空白。
- **判断**：石框的视觉质量是不错的，但这是**用一半的屏幕画边框**。在一个"每一步都要看全局"的解谜里，棋盘越大越好。
- **建议**：
  - 方案 A（推荐）：把 7×7 缩成 5×5（外框只做 4 px 描边），可玩区直接 +96%；
  - 方案 B：保留 7×7 的叙事（外框是"墙"），但**让外框参与玩法**（例如外框可被击碎 / 有缺口），把装饰变成棋盘；
  - 方案 C：至少把省下的空间分给"落点预览"和更大的步数指示。
- 注意：改尺寸会影响 `layout` 与点击命中，但 `render.js` 是纯计算，改动可控。

### 7.3 【P1】横屏不可玩

- **实测**（844×390）：格子被压到 **23 px**，棋盘 161 px，方块小到无法精确拖动；没有"请旋转设备"的提示。
- **建议**：`@media (orientation: landscape) and (max-height: 500px)` 显示全屏"请竖屏游玩"遮罩（一行 CSS + 一个 div）。横屏在 H5 里是高频场景（微信里点开、iPad 平放）。

### 7.4 【P0】选关页不定位当前关，且汇总信息是错的

- **实测**：第 50 关打开选关页时，`scrollTop = 0`，当前关在 `currentTop = 671` 而可视区底部 `624`——**当前关在屏幕外，且没有任何自动滚动**。玩家打开"选关"却看不到自己在哪一关。
- **汇总文案**：`src/main.js:333` 输出 `已获得 N 颗星 · 已开放 ${LEVELS.length} / ${TOTAL_LEVELS} 关` → `LEVELS.length` 恒为 50，所以**任何进度下都显示"已开放 50 / 50 关"**（我这次实测只解锁了 3 关，界面却写 50/50）。GDD §9.4 自己写的是"已开放 4 / 50 关"（解锁数）。
- **影响**：一个明确的**事实性错误**，会直接削弱玩家对进度的信任。
- **建议**：
  1. `已开放 ${unlockedCount} / 50`（`unlockedCount` 现有逻辑已有）；
  2. 打开时 `elLevelGrid.scrollTop = currentBtn.offsetTop - 可视高度/2`；
  3. 当前关加呼吸描边；
  4. 迷你星 9 px 太小，实机上几乎看不清"我拿了几星"——至少 11 px，或改成"数字 + 三格进度"。

### 7.5 【P1】选关页没有关卡名、没有分组

- **现状**：50 个格子，只有数字 + 3 颗迷你星。
- **影响**：无法回忆"我想要再玩一次那关有个大缺口"；也无法表达"这是第二阶段"。
- **建议**：每格下面一行 8–9 px 的关卡名（可截断），或长按/悬停显示名字；配合 5.2 的章节分组。

### 7.6 【P1】没有标题页 / 没有"作品感"

- **现状**：打开链接直接进第 1 关（或上次的关卡），没有 logo、没有标题、没有"继续 / 从头开始"。
- **影响**：作为参赛/上架作品，**玩家第一次看到的画面就是棋盘**，没有"这是一款游戏"的心理准备；也无法展示"这是《撞个正着》"。
- **建议**（半天工作量，回报很高）：
  - 一屏标题页：作品名 + 一句话规则（"撞上同色就一起消失——包括你自己的刹车"）+「开始 / 继续」+ 进度（"已获得 N★"）；
  - 标题页放一个**自动播放的 3 秒 demo**（两块方块相撞消失，再演示一次"停下来当墙"）——这是最省事的"教学 + 宣传"二合一。

### 7.7 【P2】图标语义不一致、混用 emoji

- **现状**：`☾`（主题）显示的是**当前状态**，`🔊`（声音）显示的是**当前状态**，`▦`（选关）和 `?`（提示）是**动作**。四者混用两套语义。
- **另外**：`☾ ▦ ? 🔊` 与 emoji（🔒 ★）混排，字重、基线、色彩都不统一，在高分屏上尤其明显。
- **建议**：统一成一套图标（内联 SVG 或统一字体），且统一为"显示当前状态"；`🔒` 和 `★` 也用 SVG。

### 7.8 【P2】图标按钮 30 px，低于触控最小尺寸

- **证据**：`.icon-btn { width: 30px; height: 30px; }`（`styles.css:189`）。
- **标准**：WCAG 2.5.5 / Apple HIG 建议 ≥ 44×44。
- **建议**：视觉尺寸可保留 30 px，但用 `::before` 或 padding 把**热区**扩到 44×44（不影响布局）。

### 7.9 【P2】桌面端只是"变宽的手机"

- **实测**（1000×700）：整个应用是 560 px 单列，两侧各 220 px 空白；棋盘 420 px，可玩区仍只有 300 px。
- **建议**（若目标是桌面/评委演示）：桌面下把布局改成"左侧棋盘 + 右侧信息栏（关卡名、目标、步数、par、撤销/重开、提示）"，让 1000 px 的屏幕有 1000 px 的价值。GDD 里"桌面/伴侣 UI"的设计目前完全没有实现。

## 8. 可访问性

### 8.1 【P1】颜色是唯一线索，色弱玩家基本无法游玩

- **证据**：`render.js` 调色板 `#ef4444 / #3b82f6 / #22c55e / #f59e0b / #a855f7`；方块**无符号、无纹理**（GDD §9.3 明确"内部不放任何符号"，理由是早期符号被误读为方向）。
- **色弱模拟后的可分辨度**（Machado 2009 严重度 1.0 矩阵 + CIELAB / CIE76 ΔE；经验上 ΔE < 10 在 50 px 的小方块上就"要靠猜"）：

| 色对 | 正常视觉 | protanopia | deuteranopia |
|---|---:|---:|---:|
| 紫 vs 蓝 | 45.3 | **13.0** | **1.8** |
| 红 vs 绿 | 127.3 | 37.1 | **11.5** |
| 绿 vs 黄 | 92.1 | **21.4** | 38.3 |

- **最致命的一对是紫 vs 蓝**：deuteranopia 下 ΔE ≈ 1.8，**几乎是同一个颜色**。而 50 关里有 **11 关（#34、#37、#39–#42、#45–#47、#49、#50）同时存在蓝块和紫块**——恰好集中在 S4–S5 的难点关卡。对这部分玩家，这不是"难一点"，是"这一关无法推理"。
- **影响**：约 8% 的男性玩家（红绿色弱）会遇到"紫块和蓝块长得一样"，而本作里"认错颜色"的代价是**直接走错步**，甚至直接拆掉关键的一对刹车。这不是体验问题，是**能不能玩**的问题。
- **建议**（不破坏现有视觉的最小方案）：给每种颜色叠加一个**极淡的边缘纹理**——圆点 / 斜纹 / 横线 / 网格 / 纯色（GDD §9.3 自己也提出了"只用边缘纹理"）。纹理只在方块边缘 2–3 px，不影响"按钮感"的担忧。这需要一组静态资源（或 canvas 程序化绘制），一次性成本。

### 8.2 【P2】浅色主题次要文字对比度不足

- **实测**：`--muted: rgba(16,26,44,.58)` 在 `#f2f6fc` 上 = **4.21:1**，低于 WCAG AA 对小字号的 4.5:1。
- **建议**：alpha 提到 **.62**（4.74:1）即可达标，视觉上几乎无差别。

### 8.3 【P2】模态框缺少语义与焦点管理

- **现状**：结算、失败、选关、解法都是 `<div class="modal">` + `.hidden` 切换；无 `role="dialog"`、无 `aria-modal`、无焦点陷阱、关闭后不归还焦点（部分有 `focus()`，但不完整）。
- **建议**：加 `role="dialog" aria-modal="true" aria-labelledby=...`；打开时把焦点移到第一个按钮，`Esc` 关闭，关闭后还原焦点。成本很小。

### 8.4 【P2】`user-scalable=no` 与缺少 reduced-motion

- **证据**：`index.html` 的 viewport 含 `user-scalable=no`；全站无 `@media (prefers-reduced-motion)`。
- **建议**：
  - 允许缩放（或至少允许 2×）；
  - 在 `prefers-reduced-motion: reduce` 下关掉屏幕抖动和补间，直接给结果。

### 8.5 【P2】canvas 没有键盘 / 读屏替代

- **现状**：棋盘是 canvas，键盘无法操作，读屏读不到任何棋盘状态。
- **判断**：对休闲 H5 可以接受，但若以"作品完成度"为标准，至少应提供一个**键盘方向键 + 空格确认**的操作方式（规则层已具备 `moveFrom(state,r,c,dir)`，接一个"选中块 + 方向键"的指针即可，不需要重写任何逻辑）。

## 9. 技术与工程细节

### 9.1 【P1】`npm test` 在本机跑不完

- **现象**：`npm test` 输出 npm banner 后**超过 3 分钟无任何输出**，进程持续占用 CPU（实测单进程累计 201 s CPU 后手动终止）；开发日志记录的是"约 3 秒"。
- **判断**：`tools/test_rules.mjs` 是 85 KB 的规则对拍，内部用 BFS 逐关求解并与 research 引擎对比。慢的原因很可能是某个关卡的分支爆炸（无剪枝或 `cap` 过高）。
- **影响**：新人（或评委）跑一次测试就会怀疑项目坏了；而且**一个跑不完的测试等于没有测试**。
- **建议**：
  - 加进度输出（`process.stdout.write` 每关一行）；
  - 给 BFS 加深度上限 / 状态上限，超限时**跳过并报告**而不是卡死；
  - 把 50 关对拍拆成"快速子集（前 10 关）+ 全量（CI 里跑）"。

### 9.2 【P1】生产包暴露调试接口

- **证据**：`src/main.js:606` `window.__zgz = { levels, save, loadLevel, commit, ... }`，上方注释写着「开发期调试钩子（不影响玩法；正式提交前可移除）」。
- **影响**：任何玩家可以在控制台 `__zgz.loadLevel(...)`、改 `save.best`、直接 `commit` 通关。作为参赛作品，这是**规则外的通关路径**。
- **建议**：用 `if (import.meta.env.DEV)` 包住（Vite 现成），或至少在 `build` 时通过插件剥离。

### 9.3 【P2】只有"关卡 + 星级"被持久化，刷新即丢盘面

- **现状**：`localStorage` 只存 `save.level` 和 `save.best`；刷新页面 = 当前这一关从开局重来，已走的步数与撤销历史全部消失。
- **影响**：H5 的典型使用场景是"微信里点开、切出去回消息、回来"——移动端浏览器经常回收页面，玩家会莫名其妙回到开局。
- **建议**：把 `{ state, moves, pops, history }` 序列化存入 `sessionStorage`（key 带 level id + 时间戳），加载时提示"继续上次的进度？"。同时这也是"暂停/继续"功能的基础。

### 9.4 【P2】空闲时仍在满帧重绘

- **证据**：`tick()` 无条件 `requestAnimationFrame(tick)`（`src/main.js:519`），且每帧为每个方块重建 `createLinearGradient` / `createRadialGradient`（`render.js:104/125/148/216/235`）并设置 `shadowBlur`。
- **实测**：单帧 `draw` 约 **0.153 ms**（桌面端），**不构成掉帧问题**，但手机端持续 60 fps 重绘会明显增加耗电与发热。
- **建议**：空闲（无 `drag`、无 `anim`、无主题过渡）时停止 rAF，用 `dirty` 标记按需重绘；渐变对象按 `(color, size)` 缓存。

### 9.5 【P2】无任何匿名指标，问题只能靠猜

- **现状**：没有埋点。因此"哪一关流失最多""提示被点了多少次""撤销率多高"全部未知。
- **建议**（若允许联网）：只上报 4 个事件——`level_start` / `level_win`（含 moves、是否用过提示/撤销）/ `level_fail` / `hint_click`。这四项足以回答 80% 的平衡问题。
